## 3. 预期成果

- 《需求细化与模块拆分说明》1 份；
- 《技术选型说明》1 份，明确 Web 工作台主体架构和后续 VS Code 插件扩展方案；
- 前后端项目骨架代码：Vue3 + TypeScript 前端工程、FastAPI 后端工程、基础接口示例；
- 数据库初版设计文档和建表脚本草稿；
- 论文 PDF 解析最小原型：能够输出论文标题、摘要、章节、段落、页码等结构化 JSON；
- 代码静态分析最小原型：能够输出文件树、类、函数、导入关系和 PyTorch 模型结构候选信息；
- Web 工作台低保真/静态页面原型，包括项目列表、上传页面、论文阅读区、代码浏览区和追溯结果面板；
- 第一次迭代演示材料，包括运行截图、阶段总结和下一迭代待办。

## 4. 主要的风险和应对方案

| 优先级 | 风险 | 缓解措施 | 应急措施 | 负责人 |
|---|---|---|---|---|
| 1 | 需求范围过大，进阶功能过多，导致第一周无法形成可演示闭环。 | 缓解：本迭代只保证最小闭环，即上传项目、解析论文/代码、展示结果；多模态对齐、动态追踪、魔改影响分析暂不作为第一周必须完成项。 | 应急：若进度滞后，优先保留论文解析、代码目录展示和手工追溯链接，暂缓自动匹配。 | 秦浩翔 |
| 2 | 论文 PDF 版面复杂，公式、图表和算法框识别效果不稳定。 | 缓解：第一版先提取标题、摘要、章节、段落和页码；公式和图表先记录所在页与附近文本，避免一开始追求高精度识别。 | 应急：选取 1—2 篇版式较规范的深度学习论文作为演示样例，并允许人工修正解析结果。 | 俞冠廷 |
| 3 | Python / PyTorch 代码静态分析难度较高，复杂仓库调用关系不易准确提取。 | 缓解：第一版聚焦 Python 文件、类、函数、import、nn.Module、forward 方法和配置文件，不强求完整跨文件调用图。 | 应急：对演示仓库增加规则化扫描和关键词匹配，先保证核心模型文件、训练脚本和损失函数能够被定位。 | 张朴 |
| 4 | 前后端、数据库、解析模块并行开发时接口不统一，影响联调。 | 缓解：尽早定义项目、论文片段、代码片段、追溯关系等核心 JSON 数据格式，并维护接口文档。 | 应急：使用 mock 数据支撑前端开发，后端解析结果后续按约定格式替换。 | 钱闵浩 |
| 5 | 大模型或向量检索调用成本、速度和稳定性存在不确定性。 | 缓解：第一周先以关键词匹配和向量检索原型为主，大模型解释作为可选接口；缓存分析结果，避免重复调用。 | 应急：若大模型接口不可用，使用规则匹配结果和人工说明完成演示。 | 全体成员 |
