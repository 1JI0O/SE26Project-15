## 4. 问题、变更和返工

### 4.1 遇到或已识别的问题

| 优先级 | 问题 | 影响 | 当前处理方式 |
|---:|---|---|---|
| 1 | 需求范围过大，进阶功能过多 | 可能导致第一周无法形成可演示闭环 | 将多模态对齐、动态追踪、魔改影响分析后移，第一阶段只保留最小闭环 |
| 2 | 论文 PDF 版面复杂，公式、图表和算法框识别不稳定 | 可能影响论文解析质量和追溯准确性 | 第一版先提取标题、摘要、章节、段落和页码；公式和图表先记录页码与附近文本 |
| 3 | Python / PyTorch 静态分析难度较高 | 复杂仓库调用关系不易准确提取 | 第一版聚焦 Python 文件、类、函数、import、nn.Module、forward 方法和配置文件 |



### 4.2 本次迭代中的范围变更

本次迭代的核心变更是将项目目标从“大而全的论文复现与魔改平台”收敛为“可演示的论文—代码追溯最小闭环”。具体表现为：

- 自动化能力优先级降低：第一阶段允许使用规则匹配、关键词匹配或手工追溯链接支撑演示；
- 多模态图文代码对齐后移：不作为第一周必须完成项；
- 动态运行追踪后移：不在第一阶段强制实现沙箱执行和真实张量捕获；
- 魔改影响分析后移：先保证追溯关系与一致性检查基础结构；



## 5. 经验和教训

1. **第一阶段必须控制范围。**  本项目天然容易扩展到多模态、大模型、动态追踪、魔改分析等方向，但课程第一轮迭代更需要可展示的最小闭环。先把论文和代码导入、解析、展示、追溯关系保存跑通，比追求复杂智能功能更重要。

2. **文档和接口应先行。**  前端、后端、数据库、PDF 解析和代码静态分析需要并行推进，如果没有统一的 JSON 格式和接口约定，后续联调会出现大量返工。下一步应尽快固定项目、论文片段、代码片段、追溯关系等核心数据结构。

3. **解析能力要分阶段实现。**  PDF 解析和 PyTorch 静态分析都存在很高的不确定性。第一阶段不应追求完整识别公式、图表、算法框和跨文件调用图，而应先保证标题、摘要、章节、段落、页码、文件树、类、函数、import、nn.Module、forward 等基础信息稳定输出。

4. **演示样例要尽早固定。**  为避免演示时遇到复杂 PDF 或复杂仓库导致失败，应尽早选择 1—2 篇版式规范的深度学习论文和结构清晰的 PyTorch 仓库作为样例，并围绕这些样例准备解析结果、追溯关系和截图。

5. **需要保留降级方案。**  如果自动匹配、大模型解释或向量检索效果不稳定，系统仍应能通过规则匹配、关键词匹配或人工追溯链接完成演示，保证课程迭代交付不被单个技术点阻塞。

6. **评估材料需要证据链。**  最终迭代评估不应只写“已完成”，还应补充仓库链接、提交记录、运行样例、测试记录和演示。这样可以让评审用户更容易判断迭代成果是否真实可验收。
