# TraceLab 测试、缺陷修复与质量改进计划

## 1. 计划目标

本计划用于完成构造迭代的测试与质量收口，交付以下成果：

1. 使用 pytest（xUnit 风格）测试本地后端的“仓库静态分析子系统”，所有纳入验收的自动化测试通过，语句覆盖率严格超过 90%；同时执行 `backend` 全量回归。
2. 生成可复查的终端、JUnit XML、coverage XML 和 HTML 覆盖率报告，并形成《单元测试报告》。
3. 以 `FinalRelease/系统测试用例_TraceLab.xlsx` 为历史参考，后续在 `FinalRelease/系统测试用例_TraceLab.md` 中完善并执行功能、易用性和兼容性测试；性能与可靠性测试作为可选项。
4. 对发现的缺陷建立“复现用例 -> 修复 -> 自动化回归 -> 系统复测”的闭环，发布前 P0、P1 缺陷清零。
5. 所有结果绑定到同一个候选发布版本，未实现、未执行或受环境阻塞的项目如实标记，不以占位界面、旧结果或推测结果代替测试证据。

## 2. 当前基线与关键判断

计划编制基线日期为 2026-07-28。仓库当前由 Vue 3/Tauri 前端、本地 FastAPI 后端 `backend`、可选云端同步服务 `server` 组成。

## 3. 测试范围与统计口径

### 3.1 单元测试范围

- 被测子系统：本地后端的仓库静态分析子系统，即 `backend/app/services/code_analysis` 中的归档安全解析、忽略规则、语言识别、可编辑文件、Python AST、文件树和分析汇总。
- 测试代码：继续放在 `backend/tests`，与源码共同版本管理；测试报告和证据写入 `FinalRelease`，不复制一份脱离源码的测试代码。
- 全量回归重点：项目管理、论文上传及解析状态、仓库导入和安全文件访问、代码分析及缓存、追溯生命周期及锚点恢复、Agent 会话/队列/SSE/人工确认、集成设置，以及完成后的报告导出。这些模块随 `backend` 全量测试执行，但不因此自动进入正式覆盖率分母。
- 路由级 TestClient 测试和带临时 SQLite 的子系统测试可纳入回归套件，但报告应区分纯单元测试与组件/接口测试，避免把测试数量等同于单元测试质量。
- 外部 MinerU、LLM、GitHub、SMTP 和云服务统一使用 mock、fixture 或受控测试服务，不让单元测试依赖公网和真实密钥。

覆盖率统计以课程要求允许选择的后端子系统为分母。`definition_resolve.py` 属于代码导航解析，`lsp_bridge.py` 属于桌面 LSP 兼容能力，不属于本次“仓库静态分析子系统”，因此不进入正式覆盖率分母；它们的既有测试仍随 `backend` 全量套件执行。所有范围和排除项必须在《单元测试报告》中逐项说明，不得把整个 `backend/app` 的结果冒充为本子系统结果。

覆盖范围只按职责排除，不按覆盖结果排除。RC 冻结前若该子系统新增或拆分生产文件，必须同步纳入覆盖率分母、补测并重建基线；不得继续沿用旧文件清单或旧百分比。

课程要求是“超过 90%”，因此自动硬门禁设为 `fail_under = 90.01`，避免恰好 90.00% 被误判为达标。内部冲刺目标为所选后端子系统语句覆盖率 100%；若受平台分支、不可制造的防御分支等限制未达 100%，仍必须保持严格大于 90%，并在报告中逐行说明未覆盖原因。语句覆盖率是硬门禁，分支覆盖率同时记录但暂不作为阻断门禁。

> 2026-07-28 阶段性校准：全 `backend/app` 诊断覆盖率为 73.38%（6899/9402），仅作为后续补测输入；当时的仓库静态分析子系统覆盖率为 92.80%（361/389），184 条后端测试全部通过。由于仓库仍在开发，该数字只是计划基线，不是最终验收结果；当前也没有可用的正式归档报告，最终数字必须在冻结的 RC 提交上重新生成。

> 2026-07-28 执行快照：仓库静态分析子系统已达到 100.00% 语句覆盖率（389/389，52 条定向测试通过），完整后端回归 223 条通过；报告已写入 `FinalRelease/单元测试报告`。该结果绑定到基线提交 `cfc1bc2` 与当前未提交测试工作树，功能继续变化或 RC 冻结后仍须重跑。

### 3.2 系统测试范围

| 类型 | 必测范围 | 通过标准 |
|---|---|---|
| 功能测试 | 本地项目管理、设置、PDF 导入/解析/阅读、ZIP/GitHub 或已冻结的本地目录导入、代码浏览编辑、架构图、Agent 追溯、双向定位、人工审阅、写操作确认、最终确定的报告导出。每个功能至少覆盖基本流和一个备选/异常流。 | P0 核心用例 100% 通过；全部适用功能用例通过率不低于 95%；无数据丢失或静默覆盖。 |
| 易用性测试 | 至少 3 名非当前模块作者独立完成“创建项目 -> 导入论文和代码 -> 查看架构图 -> 生成并审阅追溯 -> 编辑 -> 导出”的冻结主流程，同时检查状态反馈、错误恢复、窄屏、键盘焦点和控件语义。 | 核心任务无需开发者口头指导即可完成；无阻断性易用问题；观察问题均有记录和处置结论。 |
| 兼容性测试 | 必测最新稳定版 Chrome、Edge、Firefox，分辨率/视口至少覆盖 1366x768 和 1920x1080；最终若交付 Tauri，再测实际交付的 Windows 版本。Safari、macOS、Windows 10 等只有具备真实环境时才计为已执行。 | 核心流程、SSE、文件选择、保存和下载可用；无阻断脚本错误、页面重叠、关键控件溢出或平台专属故障。 |
| 性能与可靠性（可选） | 固定样例的项目打开、文件树切换、追溯渲染、报告生成，以及应用重启/断网恢复。 | 结果单独记录，不影响课程硬门禁；明显卡顿、数据损坏或不可恢复问题仍按缺陷处理。 |

## 4. 分阶段执行计划

### 阶段 0：版本冻结与用例重基线（2026-07-28，RC0）

1. 建立“功能 -> 源码/API -> 自动化测试 -> 系统用例”的追踪表，将功能标记为“已实现”“实现中”“可选”“本次移出”。
2. 等当前在做的新功能合并并通过基础构建后，记录候选版本的提交哈希、构建时间、配置和测试数据版本，形成 RC0；之后新增需求不直接进入本轮验收。
3. 逐条评审迁移后的 Markdown 用例：确认前置条件、步骤和预期结果与 RC0 一致；将混合多个独立故障点、不便定位缺陷的用例拆分。
4. 补充报告导出的系统用例：至少包含“真实完整项目导出 Markdown”的基本流，以及“数据不完整/生成失败/下载失败”的备选流。若该功能最终移出，必须同步修改需求、构造计划和用例适用性，不能保留为已实现描述。
5. 云端 TC-F-029 至 TC-F-036、Safari/macOS 和双设备用例在环境确认前标记“待环境确认”，不计入本地核心通过率分母。

退出条件：功能清单和参考用例完成评审，RC0 可启动，核心主流程没有已知 P0 阻断。

### 阶段 1：自动化测试基线与覆盖率设施（2026-07-28，RC0）

1. 在后端开发依赖中加入 `pytest-cov`，在 `pyproject.toml` 固化 source、omit、报告精度和 `fail_under`，同步更新锁文件。
2. 将仓库中已跟踪但指向其他机器绝对路径的 `backend/.coverage` 视为无效旧数据；后续忽略 `.coverage*`，不得把它当作正式测试证据。
3. 首次运行全部 `backend` 测试并生成 term-missing、HTML、coverage XML 和 JUnit XML 报告，记录测试总数、失败数、跳过数、耗时、语句总数、未覆盖行和实际覆盖率。
4. 执行 `server` 全部测试、后端 Ruff、前端 typecheck 和生产构建，先暴露当前回归，不把构建检查混入覆盖率数字。
5. 按未覆盖业务行和风险生成补测清单，优先级为：近期修改和历史缺陷、数据写入/状态机、安全边界、异常恢复、普通只读路径。

计划采用的最终覆盖率命令如下，实际落地后以仓库配置为准：

```powershell
Set-Location backend
uv run pytest `
  --cov=app.services.code_analysis `
  --cov-report=term-missing `
  --cov-report=html:../FinalRelease/单元测试报告/htmlcov `
  --cov-report=xml:../FinalRelease/单元测试报告/coverage.xml `
  --junitxml=../FinalRelease/单元测试报告/junit.xml `
  --cov-fail-under=90.01
```

退出条件：基线结果可复现，覆盖率缺口已落实到具体模块和负责人。

### 阶段 2：补测、缺陷修复与持续回归（2026-07-28 至 2026-07-29，RC1）

1. 优先为缺失的异常和边界行为增加 xUnit 风格测试，再修复缺陷；每个缺陷至少保留一个修复前失败、修复后通过的回归测试。
2. 每完成一个模块先运行相关测试，合并前运行 `backend` 全量测试和覆盖率；禁止仅添加无有效断言、重复 happy path 或直接调用常量的“刷覆盖率”测试。
3. 对随机性、时间、线程/SSE 和外部服务进行隔离，固定时钟、随机种子或 mock 响应，连续运行关键测试至少 3 次排查偶发失败。
4. 每次修复记录缺陷编号、影响版本、严重级别、复现步骤、根因、修复提交、回归测试和复测结果。
5. 达到覆盖率后检查 HTML 的未覆盖行，确认剩余行确属允许排除或低风险防御分支，并由另一名成员评审统计口径。

退出条件：`backend` 测试 100% 通过，仓库静态分析子系统语句覆盖率 > 90%，Ruff、`server` 测试、前端 typecheck 和 build 全部通过，P0/P1 自动化回归缺陷为 0，生成 RC1。

### 阶段 3：系统测试执行（功能冻结后，目标 2026-07-29，RC1）

1. 准备固定 PDF、合法/非法 ZIP、小型代码仓库、已解析缓存、可控 Agent/MinerU mock、空项目、历史追溯和不同权限账号；测试数据只用于测试环境。
2. 先执行本地核心基本流，再执行备选/异常流；破坏性删除、冲突、失败恢复用测试副本执行。
3. 在 Markdown 用例的执行记录中填写实际结果、状态、缺陷等级、测试环境、执行人和日期。实际结果必须描述观察到的行为，不能只写“同预期”。
4. 用例失败即建立缺陷；修复后先跑相关自动化测试，再在同一环境复测原系统用例，并记录首次结果和复测结果。
5. 功能实现中或环境不可用时使用“阻塞/未执行/不适用”状态，并写清依赖和后续安排；不得填写“通过”。

退出条件：核心功能用例全部执行，基本流和备选流覆盖完整，P0/P1 为 0，非关键适用功能通过率不低于 95%。

### 阶段 4：易用性与兼容性测试（目标 2026-07-29 至 2026-07-30，RC2）

1. 三名测试者使用同一任务卡独立操作，测试人员只观察，不提供步骤提示；记录完成时间、是否完成、错误次数、求助点和意见。
2. Chrome、Edge、Firefox 使用相同 RC2、后端和数据，分别执行核心主流程；每个浏览器至少保留版本信息、控制台结果和关键页面截图。
3. 在 1366x768、1920x1080 下检查项目列表、工作台、弹窗、论文/代码分栏、Agent 面板和报告下载；额外检查缩放 125% 时关键操作是否仍可达。
4. Tauri 只对实际要交付的安装包执行安装、首次启动、sidecar 生命周期、系统文件选择和数据持久化验证；没有实际设备的操作系统不得推测通过。

退出条件：必测浏览器和最终交付平台无 P0/P1，易用性核心任务完成，所有观察问题完成修复或进入已知限制。

### 阶段 5：最终回归与报告归档（目标 2026-07-30，Final Candidate）

1. 停止功能新增，在最终提交上重新运行全套单元/组件测试、覆盖率、Ruff、`server` 测试、前端类型检查和生产构建。
2. 对所有已关闭 P0/P1 和本轮改动涉及的系统用例做一次回归；抽查数据持久化、错误提示和敏感配置不回显。
3. 更新 Markdown 报告的结果统计，只统计实际执行且适用的用例，并单列失败、阻塞、未执行和不适用数量。
4. 完成《单元测试报告》《系统测试报告》《缺陷清单》和已知限制，保证报告中的提交哈希、测试数、覆盖率、截图和发布包来自同一版本。

最终退出条件：自动化测试全部通过且语句覆盖率 > 90%；核心系统用例 100% 通过；全部适用系统用例通过率 >= 95%；P0/P1 为 0；未关闭 P2 有规避方式和已知限制说明。

## 5. Markdown 用例的调整清单

保留 `系统测试用例_TraceLab.xlsx` 作为 1.0 历史参考，从本计划开始以 `系统测试用例_TraceLab.md` 作为唯一可维护源，并完成以下调整：

1. 在文档的执行记录表中维护“适用范围/版本”“执行人”“执行日期”“关联缺陷”“复测结果/日期”字段，状态统一为：未执行、通过、失败、阻塞、不适用。
2. 增加需求或功能标识，形成基本流、备选流到功能的可追踪关系；每项冻结核心功能至少各有一条基本流和备选流。
3. 增加报告导出基本流和备选流；根据最终范围补充或删除本地目录导入、报告下载等用例，不测试仅有占位 UI 的能力。
4. TC-F-029 至 TC-F-036 归为“云端可选功能”，与本地核心功能分栏统计。
5. TC-C-001 不再把没有测试设备的 Safari 结果合并到一个总状态；按浏览器拆成独立执行记录。TC-C-002 同理按 Windows/macOS 和具体版本拆分。
6. 对 TC-F-005、TC-F-018、TC-F-023、TC-F-035 等包含多个独立边界或恢复场景的用例，必要时拆分，确保单次失败能对应唯一原因。
7. 报告除通过率外，记录失败、阻塞、未执行和不适用数量；总体通过率使用“通过 /（通过 + 失败）”，同时单独展示执行完成率，避免把未执行项隐藏在分母外。

## 6. 缺陷管理与修复优先级

| 等级 | 判定示例 | 处理要求 |
|---|---|---|
| P0 | 无法启动、数据丢失/越权、核心演示中断、唯一交付包不可用。 | 立即停止发布，必须修复并全量回归。 |
| P1 | 核心功能错误、结果明显错误、主要浏览器不可用、关键交互无法完成。 | 发布前必须清零，相关基本流和备选流均需复测。 |
| P2 | 有明确替代路径的边界或体验问题。 | 尽量修复；保留时进入已知限制并说明规避方式。 |
| P3 | 文案、轻微样式、非验收增强。 | 不阻断发布，统一进入后续待办。 |

修复顺序固定为：安全/数据损坏 -> 启动与核心主流程 -> 状态一致性和异常恢复 -> 兼容性 -> 易用性 -> 非阻断体验。测试发现的新功能建议不直接插入本轮，除非它是关闭 P0/P1 的必要修复。

## 8. 分工与每日检查点

沿用构造迭代计划中的职责：俞冠廷统筹测试和报告，秦浩翔维护计划、覆盖率口径与交付一致性，钱闵浩和秦浩翔负责后端补测/修复，张朴负责前端修复、浏览器兼容和构建；每项最终变更由至少一名非作者成员复核。
