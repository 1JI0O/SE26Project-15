# 本地流程图与 Agent 双向追溯实现方案

## 1. 先说结论

这次要把两件事彻底分开：

| 功能 | 谁负责 | 是否需要 LLM | 什么时候运行 |
| --- | --- | --- | --- |
| 模型流程图生成、展示、节点展开 | 本地代码分析 | 不需要 | 代码导入或修改后 |
| 论文片段与核心代码的双向追溯 | Agent | 必须需要 | 论文和代码都准备好后，后台自动运行 |

流程图不能依赖 Agent、API Key、网络或模型服务。即使完全关闭 Agent，用户仍然要能看到模型主流程，并从项目函数继续展开到它内部调用的 `torch` / `nn.Module`。

追溯则相反。哪些论文片段重要、哪些代码属于核心实现、两者为什么相关，都是语义判断，必须交给 Agent。这里不再让关键词打分或本地规则代替 Agent 做结论。

## 2. 为什么不直接回退整个提交

引入“Agent 生成流程图”的主要提交是 `53a25d5`，它的上一个版本是 `78f5f33`。在 `78f5f33` 中：

- 流程图来自本地 `tensor_flow/architecture.py` 和 `semantic.py`；
- 点击可展开的项目模块时，前端直接读取本地已经分析好的下一张子图；
- 整个过程不调用 Agent；
- 本地分析已经能识别 `self.xxx` 模块、项目自定义模块以及部分 `torch` / `nn` 调用。

但 `53a25d5` 不只改了流程图，它还加入了追溯任务、论文 block 锚点、证据校验、任务进度等有用基础。因此不建议直接 `git revert 53a25d5`，否则会把追溯需要的基础设施也一起删掉。

实际实施采用“只回退流程图相关改动”的方式：恢复旧的本地流程图读取和展开路径，保留 Agent Runtime、论文锚点、追溯任务和证据校验。

## 3. 最终边界

### 3.1 本地流程图负责什么

本地分析负责：

- 从代码中选择和列出可能的模型入口；
- 生成模型主路径；
- 展示输入、输出、项目函数、项目模块、`torch` 操作和 `nn.Module`；
- 点击项目模块后继续读取其 `forward` 或实际执行函数；
- 展示节点对应的文件和行号；
- 代码版本变化后重新生成图。

本地分析不负责判断论文和代码的关系。

### 3.2 Agent 追溯负责什么

Agent 负责：

- 从论文中挑出真正值得追溯的片段；
- 从仓库中挑出真正实现论文方法的核心代码；
- 建立一对一、一对多和多对一的关系；
- 给出每条关系的相关度、理由和双侧证据；
- 明确记录无法确定的项目，不猜测路径、行号或引用。

Agent 可以读取本地代码分析产生的文件索引、符号、调用关系和流程图，把它们当作导航资料；但这些本地结果不是追溯结论，最终关系只能由 Agent 发布。

## 4. 第一部分：恢复纯本地流程图

### 4.1 后端调整

`workspace_service.get_tensor_flow()` 恢复为读取当前 `CodeRepository.analysis_json`：

```text
代码 ZIP
  -> 本地代码分析
  -> architecture_graph / tensor_graph
  -> 本地布局
  -> 流程图 API
```

流程图接口不再读取：

- `AgentAnalysisJob(kind="architecture")`
- `AgentAnalysisArtifact(kind="architecture")`
- Agent provider 状态
- Agent 模型输出

流程图 API 的 `renderer` 恢复为本地的 `architecture-dag-v2` 或 `semantic-dag-v1`。Agent 没配置、模型超时或电脑离线，都不能影响这个接口。

### 4.2 前端调整

`useTensorFlow.expandNode()` 恢复为直接请求本地子图：

```text
点击可展开节点
  -> GET flow-graph?root_symbol=...
  -> 展示该模块本地分析结果
```

这里不再创建 architecture Agent job，也不再等待 SSE。节点是否可展开，继续使用本地分析给出的 `component_symbol_id` 和 `expandable`。

### 4.3 “再向前一步到 nn.Module”怎么保证

恢复旧链路后，再补一层本地调用展开，但仍然不使用 Agent：

- 项目函数调用：解析到唯一项目符号时，继续读取该函数体；
- 项目模块调用：解析到类的 `forward` 或实际委托执行函数；
- 终点调用：显示 `torch.*`、`torch.nn.functional.*` 和 `nn.Module` 构造出的组件；
- 动态调用无法唯一解析时，显示“未解析调用”，不伪造目标；
- 默认只多展开一层，避免整张图无限膨胀；用户点击节点后仍可继续进入下一层。

也就是说，期望看到的是：

```text
Model.forward
  -> self.encode(x)
  -> Encoder.forward
  -> self.proj(x) / F.relu(x) / torch.cat(...)
```

### 4.4 清理 Agent 架构图能力

以下能力停止使用并从公开契约中移除：

- `architecture` 类型的 Agent analysis job；
- `publish_architecture_graph` 工具；
- `architecture-analysis` Agent Skill；
- 前端为了看图而创建 Agent job 的代码；
- 工作区读取 Agent 架构 artifact 的分支。

通用 Agent 框架不删除，因为双向追溯仍然需要 provider、工具调用、Run、事件流和证据校验。

数据库中的通用 `AgentAnalysisJob` / `AgentAnalysisArtifact` 表也保留，供 trace job 使用。已有 architecture 记录统一标记为 stale，并且不再参与流程图展示，不做危险的历史数据硬删除。

## 5. 第二部分：Agent 双向追溯

### 5.1 只追重点

论文不是每一段都需要连到代码。Agent 优先处理：

- 公式和目标函数；
- 公式中的关键变量、张量和参数；
- 算法步骤和伪代码；
- 模型结构图、算法图及其图注；
- 约束、损失项、更新规则；
- 对方法实现有直接说明的短段落。

默认排除：背景介绍、泛泛的相关工作、实验感想、参考文献和没有实现含义的普通叙述。

代码侧同样只追核心实现，优先处理：

- 模型和模块的 `forward`；
- 损失函数、目标函数和正则项；
- 关键张量变换与算子；
- 算法主循环、采样、更新和约束实现；
- 与论文变量有明确对应关系的参数或中间量。

默认排除：日志、参数解析、文件下载、界面代码、通用工具函数和与论文方法无关的脚手架。

### 5.2 一对多怎么存

一条 `TraceLink` 仍表示“一个论文目标到一个代码目标”。一对多通过多条关系表达，并共享同一个论文目标；反方向同理。

每条关系至少包含：

- 论文 block ID；
- block 内的精确引用文字或公式；
- 代码文件、起止行和精确引用；
- 关系类型，例如 `implements`、`defines`、`constrains`、`computes`；
- `confidence`，范围 0 到 1；
- 简短理由；
- 论文和代码两侧的证据；
- 论文版本、代码仓库和代码 revision；
- Agent Run、模型和 prompt/skill 版本。

前端把同一目标的多条关系按 `confidence` 从高到低展示。相关度是每条边的属性，不是整个分组共用一个模糊分数。

### 5.3 论文目标要比“整段文字”更精确

现有稳定 block ID 继续使用，但增加 block 内定位信息：

- `quote`：原文或公式的精确文本；
- `occurrence`：同一文字在 block 中重复时取第几处；
- `kind`：`formula`、`variable`、`constraint`、`algorithm`、`figure`、`method_text`；
- 有可靠位置时保存字符范围或 MinerU bbox；
- 无法稳定定位时不创建可悬停目标，只记录 unresolved。

后端必须验证 quote 确实存在于对应 block。不能只因为 Agent 返回了一个 block ID 就把整段高亮。

### 5.4 代码目标要精确到核心片段

代码目标保存文件路径、起止行和原文 quote。可选保存起止列，用于高亮一行中的具体表达式。

后端验证：

- 路径属于当前仓库；
- 行号属于当前 revision；
- quote 与原文件对应范围一致；
- 目标不是被忽略、过大或不可读文件；
- 同一个 revision 内目标 ID 稳定。

验证失败的关系不能进入可交互追溯结果。

## 6. 导入完成后自动后台运行

用户不应再手动点击“生成追溯”才能开始分析。增加一个很薄的追溯协调器，它只检查前置条件，不做语义分析。

触发点有三个：

1. 论文解析结果已经落库；
2. 代码本地分析已经完成；
3. 代码编辑或重新导入后，新 revision 的本地分析已经完成。

协调器每次只做这件事：

```text
当前论文存在？
当前代码存在且本地分析 ready？
Agent 已配置？
相同 paper + repository + revision 是否已有任务？
  -> 条件满足：创建 trace job
  -> 条件不满足：记录等待原因，不反复重试
```

任务指纹使用：

```text
project_id + paper_document_id + code_repository_id + code_revision + trace_skill_version
```

这样无论先导入论文还是先导入代码，第二个产物准备好后都会立即开始；重复轮询和重复打开页面不会创建多份任务。

如果没有 API Key，状态显示为 `waiting_for_provider`，不生成本地假结果，也不进入无限失败重试。用户保存 Agent 配置后，协调器自动唤醒等待中的项目。

应用重启时恢复 queued/running 任务，并重新检查 waiting 任务。代码 revision 变化后，旧关系标记为 stale，新 revision 分析完成后自动创建新任务。

## 7. Agent 实际怎么工作

trace job 使用现有 Agent Runtime，但只开放受控的只读证据工具和一个发布工具：

- 分页读取论文 blocks；
- 读取单个论文 block、公式、bbox 和图注；
- 列出仓库文件；
- 搜索仓库文本；
- 读取符号源码；
- 读取符号调用；
- 读取本地代码分析结果和本地流程图；
- `publish_trace_candidates` 发布结构化候选。

推荐分两轮完成，仍然是同一个 Agent job：

1. 先筛出少量高价值论文目标和核心代码目标；
2. 再逐条核对证据并发布关系。

本地工具负责“给资料”和“验真”，Agent 负责“选重点”和“判断关系”。本地关键词、AST 或流程图不能自行写入 TraceLink。

## 8. 悬停与高亮交互

### 8.1 默认状态

有有效追溯关系的论文目标和代码目标始终有克制但清楚的底色或下划线。普通论文内容和普通代码不加标记，从视觉上保证重点足够突出。

建议区分：

- `proposed`：较浅的追溯标记，可以直接查看；
- `accepted`：更明确的标记；
- `rejected`、`stale`：不参与正文高亮。

### 8.2 从论文悬停到代码

鼠标停在论文公式、变量、算法或关键段落上时：

- 代码编辑器打开相关度最高的文件并定位核心行；
- 对应代码片段高亮；
- 一对多时显示按相关度排序的目标列表；
- 列表显示文件、符号、相关度和一句理由；
- 用户在列表中移动时，代码高亮跟随切换。

### 8.3 从代码悬停到论文

鼠标停在有追溯标记的核心代码上时：

- 论文阅读器定位相关度最高的论文目标；
- 对应公式、变量、图或文字片段高亮；
- 一对多时同样显示排序列表并可切换。

### 8.4 防止悬停体验抖动

- 使用短暂进入延迟，避免鼠标扫过时频繁跳页；
- 浮层和目标之间移动时保持当前追溯；
- 点击目标可固定当前关系，按 Escape 或点击空白处取消；
- 只在目标变化时打开文件或滚动，不重复执行同一跳转；
- 后台分析未完成时正常阅读和编辑，不用遮罩阻塞整个工作区。

### 8.5 前端实现方式

论文侧使用现有 block anchor，在渲染后的 DOM 中按已验证 quote 包裹追溯 span；公式和图像使用对应的 KaTeX/图片容器。统一事件委托处理 hover，不给整篇 Markdown 的每个节点绑定监听器。

代码侧使用 CodeMirror decoration 标记精确行列范围，并通过 hover tooltip 读取反向索引。高亮是编辑器装饰，不修改实际代码内容。

正向和反向查询都来自同一份 TraceLink 数据，前端只建立两个索引，避免维护两套可能互相矛盾的关系。

## 9. 接口和状态

保留现有 trace job 接口，但只允许 `kind="trace"`。手动重跑仍可作为故障恢复入口，正常流程不依赖手动按钮。

增加一个适合工作区一次加载的追溯映射接口，例如：

```text
GET /api/v1/projects/{project_id}/trace-links/map
```

返回：

- 当前 paper/repository/revision；
- 后台分析状态和等待原因；
- 可交互的论文目标；
- 可交互的代码目标；
- 目标之间的关系、相关度和状态。

任务状态建议统一为：

```text
waiting_for_inputs
waiting_for_code_analysis
waiting_for_provider
queued
running
validating
succeeded
failed
stale
```

SSE 只传“正在读取论文公式”“正在核对损失函数实现”这类进度，不暴露模型思维链。

## 10. 实施顺序

### 阶段 A：拆开流程图和 Agent

- 恢复 `78f5f33` 的本地流程图读取和前端展开路径；
- 保留并完善本地向下一层的项目函数、`torch` 和 `nn.Module` 展示；
- 移除 architecture Agent job、工具、Skill 和 UI 调用；
- 用“Agent 完全关闭”的测试证明流程图仍可用。

### 阶段 B：整理追溯数据

- 扩展论文目标和代码目标的精确锚点；
- 收紧 Agent 输出 schema 和双侧证据校验；
- 支持一对多、多对一和逐边相关度；
- 对旧 architecture artifact 做失效迁移。

### 阶段 C：后台自动追溯

- 增加追溯协调器；
- 接入论文落库、代码分析完成、代码 revision 更新三个触发点；
- 处理未配置 provider、重启恢复、去重和重试；
- 移除“先跑 architecture 再跑 trace”的前端串行流程。

### 阶段 D：双向悬停交互

- 论文目标常驻标记和 hover；
- CodeMirror 精确装饰和 hover；
- 一对多排序浮层；
- 双向定位、临时高亮和点击固定；
- 分析中、失败、stale 和空结果状态。

## 11. 测试重点

### 流程图

- Agent disabled、无 API Key、断网时流程图照常生成；
- 流程图接口不会调用 provider；
- 从顶层模型可以展开到项目模块，再看到其 `nn.Module` / `torch` 调用；
- 动态调用无法解析时明确显示 unresolved；
- 代码修改后只刷新对应 revision 的本地图。

### Agent 追溯

- 没有 provider 时进入 waiting，不生成静态假关系；
- 论文和代码无论谁先完成，条件齐全后只创建一个 job；
- Agent 只能发布经过双侧 quote、路径和行号验证的关系；
- 普通背景段落和脚手架代码不会大面积高亮；
- 一对多关系保留独立相关度；
- 新 revision 使旧关系 stale，并自动分析新版本；
- fake provider 用于确定性单元测试，另外保留显式开启的真实 provider smoke test，测试报告必须标明两者区别。

### 交互

- 悬停论文目标能打开并高亮代码；
- 悬停代码能定位并高亮论文；
- 一对多目标按相关度排序并可切换；
- rejected/stale 不高亮；
- 长公式、长路径、小屏和窄面板不发生文字覆盖；
- 高频移入移出不反复跳页或造成明显闪烁。

## 12. 验收标准

完成后应当同时满足：

1. 删除 Agent 配置后，流程图生成、展示和本地节点展开不受影响。
2. 流程图能从项目函数继续看到下一层关键 `nn.Module` / `torch` 调用。
3. 流程图请求和节点展开过程中没有任何 LLM 请求。
4. 论文和代码都准备好后，无需用户点击，追溯任务自动在后台开始。
5. 没有 Agent 配置时不产生本地算法冒充的追溯结果。
6. 只有重点论文片段和核心代码被标记，不出现全篇到处高亮。
7. 论文到代码、代码到论文都可通过悬停定位和高亮。
8. 一对多、多对一关系可见，并按每条关系的相关度排序。
9. 所有可交互关系都有经过后端验证的论文证据和代码证据。
10. 版本变化、任务失败和 provider 缺失都有明确状态，不展示过期关系。

## 13. 审查时需要确认的三个产品决定

实现前建议只确认下面三点：

1. `proposed` 关系是否直接参与正文高亮。本方案建议参与，但样式比 accepted 更浅；否则首次后台分析完成后用户会看不到任何追溯入口。
2. 悬停时是否自动切换代码文件。本方案建议自动切换到相关度最高项，同时允许点击固定，才能真正做到“悬停追溯展示”。
3. 首版是否处理图片内部的局部区域。本方案建议首版高亮整张算法图或图注，公式和文字做到片段级；图片内部 bbox 热区放到下一版，避免首版被 MinerU 坐标映射拖慢。
