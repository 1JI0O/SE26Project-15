## 1. 产品一句话与定位

**TraceLab** 是本地优先的「论文 ↔ 代码」双向追溯工作台：把学术论文中的公式、算法、方法描述，精确对应到仓库里真正实现它们的代码片段，并支持悬停高亮、人工审阅与 Agent 辅助修订。

- 面向场景：论文复现、代码审阅、方法是否真正落地的核对。
- 运行形态：同一套 Vue 前端，可跑在浏览器（Web）或 Tauri 桌面端；本地 FastAPI 负责解析、分析、追溯与 Agent；可选独立云端服务器只做账号与同步，不跑分析。
- 核心原则：**语义判断交给 Agent，事实校验留在本地**。没有可靠证据就不造假链接。

## 2. 产品特色与创新点

### 2.1 论文驱动、证据校验收口的 Agent 追溯

不是「全文搜关键词再给个相似度」，而是：

1. 先识别论文里真正值得追的少量目标（公式、算法、约束、核心方法句）；
2. 再建立代码职责地图（损失、模型、数据流、训练循环等）；
3. 分区取证，读真实论文块与源码后再发布关系；
4. 发布前本地校验双侧 quote 是否在指定出现次数（occurrence）处命中，并计算内容 hash。

**创新点**：把「找关系」和「证关系」拆开——模型可以猜，系统只让过得了校验的结果进入工作台。

### 2.2 双向追溯共享同一份事实

持久化的是一张二部图：`PaperTarget ← TraceLink → CodeTarget`。  
论文到代码、代码到论文只是两个索引方向，**不是两套各自生成、可能互相矛盾的结果**。

### 2.3 三个分数分开，不混成一个「神秘百分比」

| 分数 | 回答的问题 | 归属 |
|------|------------|------|
| `salience` | 这个论文目标本身有多重要？ | 目标 |
| `relevance` | 这段代码在多大程度上承担了该目标的实现？ | 边 |
| `confidence` | 我们对「这条关系判断正确」有多大把握？ | 边 |

一对多列表按 `relevance` 排序；置信度单独展示，避免「接线调用」和「真正计算公式」被同一分数糊在一起。

### 2.4 片段级锚点，而不是整段 / 整函数糊高亮

- 论文侧：block + quote + occurrence + quote_hash（必要时 char 范围）。
- 代码侧：path + 行范围 + quote + occurrence + code_quote_hash。
- 同一句话在一段里出现多次时，能指到第 N 次，而不是「随便亮到第一次」。

### 2.5 本地优先 + 双运行壳 + 可选上云

- 默认数据在本机 SQLite 与本地文件；密钥不回传前端。
- Web / Desktop 共用前端；Desktop 用 PyInstaller sidecar 打包后端。
- 云端 `server/` 只做账号、Workspace、Blob、同步；**不执行 MinerU、AST、LLM、Agent**，项目默认 `local_only`，用户明确启用同步后才上传。

### 2.6 渐进发布与可审阅生命周期

分析边跑边落库（SSE `analysis.published`），前端矩阵与双侧高亮实时刷新。关系状态：`proposed → accepted / rejected`，版本变化可标 `stale`；重跑默认不覆盖人工决策。

### 2.7 可插拔能力面

- 论文解析：本地 MinerU / 官方 MinerU API（同一规范化输出）。
- LLM：任意 OpenAI-compatible Chat Completions。
- Agent 工具：内置 Skill + 可选 HTTP MCP。
- 语义检索（RAG）：本地离线嵌入（默认）或远程 embeddings；检索只导航，不能代替读原文发结论。

### 2.8 多入口产品形态

桌面工作台、Web、VS Code 扩展（`.tracelab/` 工作区存储）共用同一套追溯与分析理念，便于在 IDE 内审阅。

## 3. 相较于传统方式的优势

### 3.1 传统方式通常怎么做

| 传统做法 | 典型问题 |
|----------|----------|
| 人工对照论文与代码 | 慢、难复现、难共享审阅结论 |
| 关键词 / 标识符重叠打分 | 同名不同义、术语不一致时误报高；真正实现换名时漏报 |
| 静态 AST 规则硬编码「forward / loss」 | 只覆盖常见写法，对工厂模式、配置驱动、非标准入口脆弱 |
| 一次把全文 + 整库塞进大模型 | 注意力稀释、遗漏、成本高、难以审计证据位置 |
| LLM 只「解释」本地先筛出的候选 | 搜索空间仍被本地算法锁死，发现不了静态漏掉的关系 |

### 3.2 TraceLab 的对应改进

1. **下线关键词写入路径**：`/trace-links/suggest` 不再写入关系；无 Provider 时等待，不造静态假结果。
2. **Agent 自主浏览取证**：分页读论文块、搜仓库正文、读符号源码与调用点，再结构化发布。
3. **本地事实门禁**：quote / occurrence / hash / revision 校验失败则丢弃候选，不静默通过。
4. **分阶段、有界上下文**：侦察 → 制图 → 区域取证 → 归并；可并行区域子代理，但仍有预算与工具白名单。
5. **覆盖账本思维**：核心公式/算法必须有终态（linked / unresolved / 有理由排除），「没找到」是合法结论，而不是硬编链接。
6. **人机协作闭环**：自动只产 `proposed`；写操作与接受/拒绝需确认；重跑可保留历史。

### 3.3 一句话对比

传统方案多在「猜相似」；TraceLab 要求「猜完必须对得上原文位置」，并把人审、版本失效、双向浏览做成产品能力，而不是一次性脚本输出。

## 4. 追溯流程设计

### 4.1 端到端总流程（用户视角）

```text
上传 PDF → MinerU 解析落库
导入代码（ZIP / GitHub）→ 安全解压 → AST / 文件树 / 张量图
两者就绪 + Agent Provider 可用
        ↓
协调器自动创建追溯任务（也可手动重跑）
        ↓
Agent 四阶段分析 + 分批发布候选
        ↓
本地证据校验 → 写入 PaperTarget / CodeTarget / TraceLink
        ↓
工作台：矩阵、双侧高亮、悬停跳转、人工审阅
```

触发条件（任一发生且条件齐备即可）：论文解析成功、代码分析完成、revision 更新、Provider 从不可用变可用、进程启动恢复未完成任务。协调器按任务指纹幂等，避免重复建任务。

### 4.2 Agent 内部四阶段（语义层）

| 阶段 | 做什么 | 产物 |
|------|--------|------|
| 1. 论文侦察 | 摘要 + 目录 + MinerU 直接对象（公式/算法/图） | 重点地图、必查项、探索区域 |
| 2. 代码制图 | 目录、符号、调用、按需源码 | 按职责组织的实现地图（不是文件树照抄） |
| 3. 区域取证 | 对每个区域：提精确论文目标 → 搜索意图 → 读代码 → 反证 → 发布或 unresolved | 候选边 / 未解决项 |
| 4. 归并自校 | 去重、冲突处理、覆盖账本收口 | 经本地校验后的可交互关系 |

当前实现：单次 `AgentAnalysisJob` / 单 Run 内顺序走四阶段；阶段 3 可通过 `dispatch_trace_subagents` 把多个区域派到有界线程池并行，经**单写者发布汇**串行落库，事件总线保证 SSE 序号单调。

### 4.3 责任边界（必背）

| 谁 | 负责 | 不负责 |
|----|------|--------|
| 本地基础设施 | 安全路径、分页、符号行号、证据校验、任务调度、布局、持久化 | 判定「这段代码是不是那个公式」 |
| Agent | 选重点、理解语义、判断对应关系、写理由与分数维度 | 绕过校验直接写库；执行用户仓库代码 |
| 用户 | 接受 / 拒绝 / 修订 | 被系统静默覆盖已做决策 |

### 4.4 数据模型（答辩常问「怎么存」）

```text
PaperTarget（论文片段）  ←── TraceLink（原子边）──→  CodeTarget（代码片段）
```

- 一对多 / 多对一 = 多条边，每条边各自有 relevance、confidence、证据与理由。
- 关系类型示例：`implements`、`computes`、`defines`、`constrains`、`updates`、`configures`、`invokes`。
- 身份不以易漂移的 block 序号为唯一依据：论文侧用 quote + occurrence + hash；代码侧重 quote + occurrence + hash。

### 4.5 前端双向交互

- 常驻装饰：仅当前 revision 的 `proposed`（浅标记）与 `accepted`（更明显）。
- 悬停：对侧定位到 relevance 最高的目标，浮层列出全部相关项并可切换。
- 点击固定，Esc 取消；选中 / 悬停 / 滚动三条通道解耦，避免互相抢滚动。
- 公式块用归一化 TeX 与 KaTeX annotation 对齐，**绝不**回退到「文档里第一个公式」。

### 4.6 版本与失效

- 任务绑定论文版本 + 代码 revision + Skill/schema 版本等快照。
- 代码保存或重解析后，旧结果可标 `stale`，不再作为默认高亮。
- 重跑按 fingerprint upsert：`accepted` / `rejected` 不被自动覆盖。

## 5. 置信度与评分设计

### 5.1 为什么不能只用一个 confidence

「相关」≠「确信」。例如：训练循环里调用 `loss_fn` 的那一行，判断「确实调用了损失」可以很确信（高 confidence），但真正计算公式的是 `loss_fn` 内部（高 relevance）。混成一个分会误导审阅优先级。

### 5.2 默认模式（项目未开深度思考）

Agent 直接给出 `salience`、`relevance`、`confidence` 三个分，服务端原样落库。  
`prompt_version = trace-agent-v2`。  
适合要速度的日常分析。

### 5.3 深度思考模式（`project.agent_deep_thinking = true`）

Agent **不再直接定 confidence**，而是给六个 `[0,1]` 维度；服务端函数 `compute_trace_confidence` 按加权公式计算，并应用减分项。  
`prompt_version = trace-agent-v3`，维度写入 `score_basis_json`。

#### 公式

\[
confidence = clip_{[0,1]}\Big(\sum_i w_i \cdot d_i + \sum_j p_j\Big)
\]

结果保留 4 位小数。

#### 六维权重（和为 1.0）

| 维度（英文键） | 含义（答辩可用白话） | 权重 |
|----------------|----------------------|------|
| `change_directness` | 论文概念与代码片段是否直接对应，而不是拐了好几层包装 | 0.20 |
| `causal_reachability` | 是否沿调用/数据流能讲清「从入口到这段计算」 | 0.25 |
| `requirement_support` | 论文是否明确要求了这件事（不是过度推断） | 0.20 |
| `trace_support` | 是否有本项目已复核先例可作参考（仅校准，不能当本轮证据） | 0.15 |
| `verification_support` | 是否有测试或可核对线索支撑 | 0.10 |
| `context_coverage` | 相关文件/上下文是否读够，而不是只看了一眼 | 0.10 |

#### 减分项（可多选，未知键忽略）

| 键 | 减分 | 含义 |
|----|------|------|
| `paper_association_inferred` | −0.10 | 与论文的关联偏推断 |
| `no_call_entry` | −0.20 | 找不到可靠调用入口 |
| `alternate_implementation` | −0.20 | 存在替代实现，当前匹配不唯一 |
| `config_or_caller_unread` | −0.15 | 配置或调用方未读到 |
| `context_truncated` | −0.15 | 上下文被截断 |
| `runtime_condition_unverified` | −0.15 | 依赖运行时条件，静态无法核实 |

#### 回退规则

若六维全停在默认值且无减分项，说明模型没认真填维度 → **回退到模型自报的 `confidence`**，避免空跑公式。默认全默认时加权基线约 0.625。

### 5.4 与静态旧方案的区别（若被问到历史）

早期 `static_candidates` 用 token / 引用重叠打分，并可叠加 LLM 解释分（`static_confidence` / `llm_confidence`）。该**写入路径已退役**；现主路径 `source=agent`，`static_confidence=0`，置信度来自 Agent（或深度思考公式）。

## 6. 我们微调 / 迭代了什么

这里的「微调」主要指**产品与管线迭代**（提示词、评分、校验、架构分期），不是训练自家大模型权重。答辩可按时间线说：

### 6.1 从「静态候选 + LLM 解释」到「Agent 独占语义」

- 停用关键词候选写入，避免无 Provider 时仍冒出假追溯。
- 新增分析专用发布工具 `publish_trace_candidates` / `publish_architecture_graph`，普通聊天自然语言不能直接落库。

### 6.2 评分体系演进

- v2：三分（salience / relevance / confidence）分离。
- v3（可选深度思考）：confidence 改为六维加权 + 减分，服务端重算，可审计。
- 深度思考默认关闭：多维评估明显变慢，按项目开关。

### 6.3 锚点与校验加固

- 引入 occurrence、quote_hash / code_quote_hash。
- 发布时「指定第几次出现」命中，失败即拒。
- 公式用 TeX 归一化对齐渲染结果，禁止错误回退高亮。

### 6.4 编排能力增强

- 协调器自动后台启动。
- 有界并行区域子代理 + 单写者发布汇 + 线程安全事件总线。
- 渐进发布：边分析边展示。
- 手动中止检测、job 结束一次性写回大 JSON，减轻 SQLite 写压力。

### 6.5 RAG 作为加速层（非结论层）

- 论文 / 代码 / 已复核追溯三域索引。
- 默认本地签名哈希嵌入（离线、确定性）；可切远程 embeddings。
- 检索结果只缩小搜索范围；系统提示明确：先例不可当本轮证据复用。

### 6.6 提示词与 Skill 约束（实质「对齐」手段）

- `trace-analysis` Skill：只选有实现意义的目标、先搜索意图再取证、无证据则 unresolved、主动找反证。
- 注入已复核先例作少样本校准，并声明不得直接复用结论。
- 分析预算：interactive ~18 步；architecture ~48；trace ~64；必须调用发布工具才算完成。

### 6.7 工程可靠性修补（答辩可举「我们踩过的坑」）

- 迁移漂移导致缺列 → 幂等修复迁移 + SQLite 兼容升级路径。
- 并发读论文任务状态文件短暂 404 → 读写同锁。
- 远程 embedding 非法响应统一降级错误码。
- 删除已复核追溯后先例索引失效标记。

## 7. 架构设计（接口驱动与设计模式）

### 7.1 总体架构：本地优先、单体后端、双运行壳

```text
浏览器 / Tauri WebView
        ↓  /api/v1（Axios + Agent SSE）
FastAPI 路由层（校验、DTO、异常映射）
        ↓
领域服务层（论文 / 代码 / 追溯 / Agent / RAG / 工作台）
        ↓
SQLModel + SQLite    本地 uploads/data 文件
        ↘ 可选
独立 server/（账号、同步、Blob；PostgreSQL）
```

分层清晰：**接口契约按领域拆分**（`docs/contracts/papers|repositories|traces|agent|rag|cloud-sync.md`），前后端、桌面与扩展都按契约演进，而不是「一个大杂烩 API」。

### 7.2 基于接口（Protocol / 契约）的设计

| 位置 | 做法 | 好处 |
|------|------|------|
| `DocumentParser`（Protocol） | 解析器统一 `parse(path) → ParseOutcome` | 本地/官方 MinerU、测试 stub 可替换 |
| `MinerUClientProtocol` / `TransportProtocol` | HTTP 传输可注入 | 单测可 mock，不打真网 |
| `TraceExplanationProvider`（Protocol） | 旧 LLM 解释可插拔 | 降级路径清晰 |
| RAG embeddings | `local` / `remote` 两种实现 | 无密钥也能检索导航 |
| OpenAPI + Pydantic schemas | 请求响应强类型 | 前后端类型对齐、非法输入早失败 |
| Agent 工具注册表 | Skill / Tool / MCP 统一能力快照 | enabled + trusted 双开关，审计可回放 |
| FastAPI `Depends(get_session)` | 依赖注入 Session | 测试可换内存库 |

**答辩表述**：我们把「能换的外部能力」都收成接口，业务只依赖抽象；换 MinerU 源、换 LLM、换嵌入方式，不改工作台主流程。

### 7.3 应用的设计模式（结合源码说）

| 模式 | 在项目中的落点 | 解决什么问题 |
|------|----------------|--------------|
| **分层架构** | routes → schemas → services → models/db/storage | 表现与业务解耦 |
| **工厂方法** | `document_parsers/factory.create_mineru_parser` | 按配置创建解析器 |
| **策略模式** | MinerU local/official；embedding local/remote；深度思考开/关两套评分策略 | 同一流程多种算法 |
| **适配器** | Official/Local MinerU → `normalizer` → 统一 `ParsedDocument` | 抹平上游格式差异 |
| **仓储 / 会话** | SQLModel Session + 实体 | 持久化集中 |
| **依赖注入** | FastAPI Depends；测试覆盖 DB/LLM | 可测、可替换 |
| **观察者 / 事件流** | AgentRunEvent + SSE cursor；`SharedRunEventBus` | 进度推送、前端增量刷新 |
| **发布-订阅式进度** | `analysis.published` 渐进合并 | 长任务不等全部结束 |
| **单写者（汇）** | `TracePublishSink` | 并行子代理落库不打架 |
| **命令 + 确认门禁** | 写工具 → `AgentToolRequest` pending → 用户 accept/reject | 防止 Agent 擅自改代码/追溯 |
| **状态机** | TraceLink status；AnalysisJob status；协调器 waiting_* | 合法迁移、幂等审阅 |
| **外观 / 聚合读模型** | `workspace_service` 聚合论文/代码/矩阵 | 工作台一次拉齐 |
| **内容寻址缓存** | 论文解析 content-hash 缓存 | 相同 PDF 不重复解析 |
| **Sidecar** | Tauri 启动打包后端 | 桌面分发免装 Python |
| **Outbox** | 本地同步 outbox | 可靠上云删除/变更 |

### 7.4 安全与边界设计（架构层面）

- ZIP：拒绝对路径、`..`、symlink；限制数量与展开大小。
- 代码编辑：相对路径白名单、覆盖目录，不改原 ZIP。
- Agent 分析工具：绑定项目与 revision，限制字符与路径；无 shell / 无任意文件系统。
- 密钥：`SecretStr`，设置接口只返回「是否已配置」。

### 9.2 质量门（追溯业务侧）

发布前本地校验至少包括：

- 论文 quote 在指定 occurrence 命中，hash 一致；
- 代码路径在仓库内，行列有效，quote 在指定 occurrence 命中；
- relevance / confidence 合法并带评分依据（深度思考时含六维）；
- 不覆盖用户已 accepted / rejected 的决策。

设计原则：**无关系不是失败**；核心对象未找到应记 `unresolved`，而不是编造。

## 10. 可能被追问的边界与诚实回答

**Q：你们有没有自己微调（fine-tune）大模型？**  
A：当前产品路径是 **提示词 / Skill / 结构化 schema / 服务端评分公式 / 证据校验** 的系统级对齐，对接任意 OpenAI-compatible 模型（如 DeepSeek）。没有把私有论文-代码对做成训练权重发布为必需依赖；这样更易换模型、也更符合本地优先与密钥自管。

**Q：准确率能到多少？**  
A：应以固定样例集上的重点召回、关系准确、锚点有效、无关高亮等指标回答；架构文档要求建立 ground-truth fixture。实测案例（文档记载）在真实仓库上能产出可审阅的 proposed 关系且平均置信度较高，但**不能用单次平均值代替系统测试结论**。最终以人工审阅为准，系统默认不自动 accept。

**Q：LLM 挂了怎么办？**  
A：追溯任务等待或失败，保留上一版并标 stale；**不**回退到关键词假结果。代码分析、张量流仍可本地运行。

**Q：张量流图挂了会影响追溯吗？**  
A：不会。张量流是独立静态可视化；追溯 Agent 工具白名单不依赖图发布。更影响质量的是符号索引是否为空。

**Q：一对多怎么表示？**  
A：多条 `TraceLink` 共享同一 `paper_target_id`（或代码侧相反）；UI 按目标分组，按 relevance 排序。

**Q：为什么强调本地校验？**  
A：大模型会幻觉路径与行号。没有 occurrence/hash 门禁，高亮错位看起来就像「追溯错了」，比明确 unresolved 更糟。

**Q：和 IDE 里「找引用」有何不同？**  
A：找引用是符号级导航；我们做的是**跨模态语义对应**（论文公式/方法句 ↔ 实现片段），并带审阅状态、证据与版本。

**Q：云端会不会看到我的论文和代码？**  
A：分析默认在本地；只有用户明确启用项目同步才会上传约定范围。使用远程 LLM 时，**被选中的论文区域与代码片段会发往 Provider**——设置与任务状态需明示；分区取证用于减少不必要外发。

## 附录 A：答辩可用「60 秒电梯稿」

TraceLab 解决论文复现时「这段公式到底对应哪段代码」的问题。我们不用关键词碰运气，而是让 Agent 按「侦察 → 代码地图 → 分区取证 → 归并」读真实证据，再由本地校验 quote 位置与内容 hash 后才写入关系。三分评分分清重要性、实现相关度和把握；可选六维加权置信度让分数可解释。Web 与桌面共用前端，数据默认本地，云端只做可选同步。测试上对关键子系统设覆盖率门禁，并用证据校验与人工审阅保证结果可审计。
